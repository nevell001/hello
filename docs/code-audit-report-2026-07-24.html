C-1. CacheManager 并发安全：LinkedHashMap access-order 在读锁下导致竞态条件
Critical 并发安全 CacheManager.java:31-48
productCache 使用 LinkedHashMap(128, 0.75f, true) 开启 access-order 模式，每次 get() 会修改内部链表结构。但 getProductFromCache 等方法使用读锁（ReadWriteLock），允许多线程同时进入，导致非线程安全的结构修改。高并发下可能死循环或数据损坏。
// accessOrder=true — 每次 get() 修改链表结构 private static final Map<Integer, Product> productCache = new LinkedHashMap<Integer, Product>(128, 0.75f, true) { ... }; // 使用读锁，但 get() 并非只读操作 lock.readLock().lock(); // 多线程同时持有 try { return productCache.get(productId); // 修改链表 → 竞态条件 } finally { lock.readLock().unlock(); }
修复建议：将 accessOrder 改为 false（放弃 LRU 自动排序），或将读操作改用写锁。最佳方案：替换为 ConcurrentHashMap + 手动 LRU，或引入 Caffeine/Guava Cache。
C-2. ExportUtil 路径遍历漏洞
Critical 路径遍历 ExportUtil.java:55-88
export() 方法的 subDir 和 title 参数直接拼接到文件路径中，未做任何路径遍历检查。攻击者传入 subDir="../../etc" 可将文件写到导出目录之外。
Path exportPath = Paths.get(EXPORT_DIR, subDir); // subDir 未验证 String filePath = exportPath + File.separator + fileName + ".xlsx";
修复建议：验证 subDir 不含 ".." 和路径分隔符；用 Path.normalize() 并校验结果仍在 EXPORT_DIR 内：if (!exportPath.startsWith(EXPORT_DIR)) throw new SecurityException(...)。

C-4. BatchOperationUtil SQL注入 + 不安全的 LOAD DATA INFILE
Critical SQL注入 BatchOperationUtil.java:107-148
optimizedBatchInsert 通过 String.format 拼接 LOAD DATA LOCAL INFILE SQL，tableName 和 delimiter 直接插入。临时文件路径硬编码 /tmp/，Windows 不兼容。LOAD DATA LOCAL INFILE 本身要求 MySQL 开启 local_infile=1，是安全风险。
String tempFilePath = "/tmp/batch_insert_" + System.currentTimeMillis() + ".csv"; // Windows 不兼容 String sql = String.format( "LOAD DATA LOCAL INFILE '%s' INTO TABLE %s FIELDS TERMINATED BY '%c'", tempFilePath, tableName, delimiter // tableName 未验证！ );

C-5. 会员余额更新缺少乐观锁（并发扣款可能丢失余额）
Critical 并发安全 / 事务 MemberDAO.java:307-322 · MemberService.java · TransactionService.java:129-164
MemberDAO.updateWithConnection 的 SQL WHERE 子句只有 id=?，没有 version 字段。采用"读最新值→内存计算→覆盖写入"模式时，两个并发事务可能同时读到相同旧余额，各自计算后写入，后写覆盖先写，导致余额丢失。对比 ProductDAO 已有乐观锁（WHERE id=? AND version=?），会员却没有。
// MemberDAO — 无乐观锁 String sql = "UPDATE members SET ... balance = ? WHERE id = ?"; // 没有 version 条件 // ProductDAO — 已有乐观锁 String sql = "UPDATE products SET ... version = version + 1 WHERE id = ? AND version = ?";
修复建议：为 members 表添加 version 字段，UPDATE 增加 AND version = ? 条件，SET 中 version = version + 1。与商品乐观锁保持一致。影响范围：MemberService.recharge / TransactionService.executeTransaction / ReturnService.completeReturnOrder。

Critical 事务管理 DataService.java:170-183, 229-242, 46-72, 296-305

// 先删除全部 → 再插入 → 中间失败 = 数据全没了 List<Promotion> existing = PromotionDAO.findAll(); for (Promotion p : existing) { PromotionDAO.delete(p.id); // 逐条删除，无事务 } PromotionDAO.batchInsert(promotions); // 如果失败，数据已丢失

C-7. 金额字段使用 double 类型导致精度丢失

修复建议：将所有金额参数从 double 改为 BigDecimal。调用方直接传入 BigDecimal.valueOf(string) 或 new BigDecimal("100.00")。
